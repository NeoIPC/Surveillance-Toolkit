## PowerShell

- **Always** restore the caller's environment before a script returns. A script run **in-process** (`.\Foo.ps1`, `& .\Foo.ps1`, dot-sourced) shares the caller's environment, so every `$env:` assignment persists and reaches every later child process; `pwsh -File` forks, which is why CI never shows it. Two consequences make it a defect: **credentials persist** in the session (`NEOIPC_DHIS2_TOKEN`, `NEOIPC_DHIS2_PASSWORD`), and **safety switches persist**, so a leftover override of a fail-closed gate silently disables it on a later run that never asked for it. Wrap the work in a save, apply, and `finally`-restore helper rather than assigning `$env:` directly, with two load-bearing details: (1) restoring **removes** a variable the caller did not have, with `[Environment]::SetEnvironmentVariable(name, [NullString]::Value, 'Process')`, since `$null` binds to the `[string]` parameter as `''` and leaves it empty but **present**, so a consumer's default-when-unset fallback never fires; (2) a fail-closed switch is set on **both** branches (`'1'` or `'0'`), never only when enabled, or an inherited value decides it. `finally` covers return, `throw`, and `exit`; a killed process takes its environment with it. *(PowerShell-specific)*
- **Never** name a variable after a PowerShell **automatic variable**: it shadows the engine's own and usually still works, until an unrelated reordering changes the answer. Check the name against the engine, since a list from memory misses names such as `CurrentlyExecutingCommand`, `OFS`, and `PSStyle`: `pwsh -NoProfile -Command 'Get-Variable | Select-Object -ExpandProperty Name'`, less the preference variables and settable knobs, which exist to be assigned. `$null = <expr>` is the discard idiom but reads like a mistyped `$null -eq $value`, so judge it by the right-hand side: a call is a discard, a bare variable a bug. PSScriptAnalyzer's `PSAvoidAssignmentToAutomaticVariable` enforces the rule. *(PowerShell-specific)*
- **Always** pass `-Depth 100`, the parameter's maximum, to `ConvertTo-Json`: its default of **2** silently drops everything deeper while the output still *looks* like JSON, and the only signal is a warning on a stream nobody reads in CI. The **error path is the untested path**: a nested error object degrades into a stringified hashtable (`@{line=1; column=9}`) in exactly the run someone is reading, so the rule is unconditional, and nothing in this project is defended against depth. `Test-ConvertToJsonDepth` in [`scripts/Test-TextFileHygiene.ps1`](../../scripts/Test-TextFileHygiene.ps1) flags a call with **no `-Depth`**, matching on the AST, since most textual hits are the phrase inside a comment; it does not check the value, so an explicit lower `-Depth` passes, and it leaves a splatted call alone, whose hashtable it cannot read. *(PowerShell-specific)*

### Writing Text Files

`Set-Content` and `Out-File` join items with `[Environment]::NewLine` and append one more, and `ConvertTo-Json` indents with it, so even `[System.IO.File]::WriteAllText` of its output is CRLF on Windows: normalize the line endings at the write point.
