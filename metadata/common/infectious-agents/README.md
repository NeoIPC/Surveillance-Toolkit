# Infectious Agents

This directory contains the NeoIPC infectious-agent ontology, `NeoIPC-Infectious-Agents.yaml`, from which the DHIS2 `NEOIPC_PATHOGENS` option set behind the infectious-agent pickers, and the program rules that classify the infectious agent recorded, are generated. It is written in YAML 1.2.2's portable subset, which YAML 1.1, YAML 1.2.2, and the YAML readers the toolkit meets read alike: every plain scalar reads as one type and value in each of them, every plain key as a string, and every block scalar as a string whose final line break none of them gains or loses, and there are no anchors, aliases, tags, directives, second documents, keys that are collections, or keys repeated, in the same or another letter case. The Core Protocol's printed list of infectious agents (`New-PathogenList` in the NeoIPC-BuildTools module) renders from the frozen CSVs kept beside it, which two readers outside this repository also download. Beside the ontology, `NeoIPC-Infectious-Agent-Reporting-Groups.yaml` sorts its infectious agents into groups for reporting ([Reporting Classification](#reporting-classification)).

## Adding an Entry

Only the entries a user can select carry an `Id:`, a unique integer that is the option code in DHIS2 and the join key in downstream tools; structural nodes, most higher ranks among them, carry none. To find the next unused integer:

```powershell
Import-Module ./scripts/modules/NeoIPC-Tools
Find-NextFreeInfectiousAgentId
```

The cmdlet returns `max(existing Id:) + 1`, a new `Id` on `main`, which keeps every released `Id`. On a branch that maintains an earlier line, take one above every `Id` any release has used instead, since a later line may already have given the file's next integer to another infectious agent. `Id`s are append-only: an `Id` once released never disappears from the list (a branch that maintains an earlier line need not carry the `Id`s a later line added), and a renamed or reclassified infectious agent keeps its old name as a synonym, with its original `Id`, since collected records hold that `Id`, while the new name takes the next free one. Only an `Id` that was never released can leave a gap, and a gap is not refilled, so no downstream consumer meets an `Id` reused for another infectious agent.

Once the new entries are in the file, draw each new `Id`'s DHIS2 UID, which its option takes from the UID sidecar:

```powershell
Add-NeoIPCInfectiousAgentUid
```

A row, once drawn, never changes: every instance that imported a package carrying the option holds it under that UID, and refuses another option of the set with the same code or name. An entry that a branch maintaining an earlier line takes from `main` therefore takes its row with it, rather than drawing another.

`MetadataContent.Tests.ps1` in the NeoIPC-Tools module holds the committed list to these checks, each shown firing on a fixture in `InfectiousAgentValidation.Tests.ps1`:

1. every key is one the list's vocabulary has at its place, in its spelling, and every `Id`, record number, and flag is written in its plain form: an `Id` as an integer from 0 and a record number as one from 1, both up to 2,147,483,647, and a flag as one of YAML 1.2.2's plain Booleans (`true`, `True`, `TRUE`, `false`, `False`, or `FALSE`);

3. every node can be told from every other: a synonym has an `Id` of its own, since a value collected in DHIS2 may be its `Id`; no two nodes of one source share a `ConceptId`, no two LPSN nodes a record number, no two MycoBank nodes a MycoBank number, which a link to a name takes, and no two concepts an `IctvId`, which repeats only among a concept and the synonyms that are its former names; and a NeoIPC `ConceptId` is an integer from 1;

5. the option labels generated from the list are distinct, as DHIS2's metadata import requires of the options of one option set, and fit the 230 characters DHIS2 stores;
6. the UID sidecar gives every `Id` of the list, and nothing else, a well-formed DHIS2 UID of its own;
7. the list is append-only against every released version, the `infectious-agents-v*` tags: a released `Id` keeps its name and the UID a release's sidecar gave it, an `Id` new since the releases exceeds every released one, and a released `Id` never disappears, nor does its UID, except from a branch that maintains an earlier line, which need not carry the `Id`s of a later line's releases outside its history (those of a greater MAJOR.MINOR than its `VERSION` file names). The check reads the tags, so it fails rather than passes in a clone without them, or without the tag of a release the CHANGELOG records; only the release that the `VERSION` file names needs no tag while the CHANGELOG's `[Unreleased]` section lists no change, as while that release is prepared, since its tag names the commit that merges the preparation. Until that tag is pushed, a clone cannot tell the release from its preparation, so the tag is pushed before the next change to the list merges;
8. the two frozen CSVs are unchanged.

## Ontology Structure: Flag Inheritance and Virus Classification

The ontology is a tree: every node may carry child nodes under `Hierarchies`, `Synonyms`, and `Children`. **A synonym is a first-class, Id-bearing, selectable option**, not just a display alias — a value collected in DHIS2 may be a synonym's `Id`, so downstream classification must treat synonyms exactly like the concepts they belong to.

Two classification mechanisms follow from this, and both are relied upon by the generated DHIS2 program rules (the `set recognized pathogen` / `set virus` ASSIGN rules) **and** by the synthetic-data generator that must produce rule-valid data:

- **`CommonCommensal` (and resistance) flags are inherited.** A node's **effective** flag is the nearest explicit value on its path to the root: its own value if it carries one, otherwise the closest ancestor that does; absent everywhere it defaults to `false`. The flag **flows down** through `Hierarchies`/`Synonyms`/`Children`, so setting `CommonCommensal: true` on a genus marks every species and synonym beneath it without repetition — and an **explicit `false` on a descendant overrides an inherited `true`** (and vice versa). This is why you cannot read a node's flag in isolation: *Staphylococcus epidermidis* carries no flag of its own and is a common commensal through the *Coagulase-negative staphylococci* group node above it. Resistance flags (`MRSA`, `VRE`, `3GCR`, carbapenem, colistin) use the identical own-or-inherited model.
- **Virus classification is structural, not a flag.** There is no per-concept "kingdom" attribute. A concept **is a virus if and only if it descends from the top-level `Viruses` node**, NeoIPC's own node above ICTV's realms — mirroring how bacteria live under `Bacteria` and eukaryotes under `Eukaryota`. Because synonyms are Id-bearing options too, the virus set is the **full subtree** under `Viruses` (every concept *and* synonym Id), so a value entered against a virus synonym still classifies as a virus.

The canonical implementations are `Get-NeoIPCCommonCommensalFlag` / `Get-NeoIPCCommonCommensalCodeSet`, `Get-NeoIPCResistanceFlag` / `Get-NeoIPCResistanceCodeSet`, and `Get-NeoIPCVirusCodeSet` in the `NeoIPC-Tools` module — the single source both the rule generator and its tests expand from. Outside the module, `Get-NeoIPCInfectiousAgentCodeSet` returns the sets they give, with the concepts, the synonyms, and the SHA-256 of the list, and `Export-NeoIPCInfectiousAgentCodeSet` writes them as JSON for a consumer in another language. Compute effective flags/sets through those rather than reading a node's literal `CommonCommensal` value or guessing at kingdom membership.

NeoIPC's own prose about a node sits in its `Comments`, a mapping of texts: under a flag's key, the reason for that flag, on the node that carries it; under `CommonCommensal` on a node without that flag, why none sits there although one would hold for every `Id`-bearing node beneath it; and under `Background`, anything else.

## Reporting Classification

`NeoIPC-Infectious-Agent-Reporting-Groups.yaml` is a classification above the ontology that groups its infectious agents for reporting and leaves the ontology as it is: the ontology says what an infectious agent is, the classification how a report groups it. Its `Groups` form a tree whose leaves list their `Members`, nodes of the ontology named by `ConceptSource`, `ConceptId`, and `Name`, higher ranks without an `Id` among them, and every `Id`-bearing node belongs to the group of its nearest listed ancestor-or-self, a synonym to its concept's. A member beneath a member of another group overrides it and says why in its `Reason`, and a member of a group that shares its ECDC category with another names in its `Reason` the property that sets it in its group, which the file shows nowhere else, such as its use of glucose, what makes it one of the other bacteria, or its growth as a yeast or a mould. The `Id`s 0 (*Not listed*) and 3561 (*Unidentifiable*) belong to no group, since neither says what the infectious agent was. A group's `Key` is a stable identifier, never translated, while its `Name` and its `Definition`, which says what the group holds, are in the translation catalogue, and its own `Evidence` cites the work its `Definition` rests on: ECDC's protocol for a group that follows a category or the codes of its annex, and the work that describes the property on which a group of NeoIPC's own turns. A group bears the `Name` of a node of the ontology only where it holds every `Id`-bearing node beneath that node, since the two then share one entry of the catalogue, and with it one translation.

The tree follows the categories of Annex 1 of ECDC's protocol for the surveillance of healthcare-associated infections in intensive care units ([Data Sources](#ecdc-hai-net-icu-protocol)), and each group of members names, as its own `EcdcCategory` or that of the group above it, the category its figures are set against:

1. **Bacteria**, in ECDC's categories:
   - Gram-positive cocci, Gram-negative cocci, Gram-positive bacilli, and Enterobacterales;
   - the Gram-negative bacilli outside the Enterobacterales, which NeoIPC splits into non-fermenting, fermenting and fastidious, and variably fermenting ones;
   - anaerobes;
   - other bacteria, which NeoIPC splits by what they are into actinomycetes (the group *Actinomyces*, *Nocardia*, and related bacteria), mycobacteria, bacteria without a cell wall, obligate intracellular bacteria, and spirochaetes;
2. **Fungi**, which NeoIPC splits into yeasts, moulds, and other fungi, which hold the fungal taxa that span yeasts and moulds, as the annex's codes split its Fungi category into *Candida* and other yeasts, *Aspergillus* and other filaments, and other fungi;
3. **Viruses**;
4. **Parasites**, the infectious agents among the eukaryotes that are no fungi. ECDC has no category of parasites and counts them in its Fungi category, so the group carries that category.

An infectious agent that ECDC's annex names sits where the annex puts it, and so does a genus formed since December 2010, when ECDC's first HAI-Net ICU protocol set the codes of its annex, for a type species that until then stood in a genus the annex names, citing the work that formed it. Any other sits by these conventions, the first that applies deciding, each applied to the properties of its genus:

1. the mycobacteria and the bacteria without a cell wall, which the Gram stain does not classify, the obligate intracellular bacteria, and the spirochaetes are other bacteria, each in its subgroup, and so are the actinomycetes: *Actinomyces*, a genus the annex counts among the other bacteria, the genera formed for a type species then in it, and the aerobic actinomycetes that clinical microbiology groups with *Nocardia*;
2. an obligately or aerotolerant anaerobic bacterium is an anaerobe, whatever its Gram reaction and shape, as ECDC's anaerobes join Gram-positive and Gram-negative genera;
3. any other bacterium sits by its Gram reaction and its shape, cocci with the cocci, rods and coccobacilli with the bacilli, as are the helical bacteria other than the spirochaetes, since ECDC counts *Campylobacter* and *Helicobacter* among the Gram-negative bacilli, and the order Enterobacterales with the Enterobacterales; a Gram-positive genus whose cells range from cocci to rods counts among the bacilli, as the coryneform bacteria do, unless its description gives them as mainly or typically cocci, and a genus whose description gives it as Gram-variable, or gives no Gram reaction, takes the Gram reaction of its class, or else of its phylum;
4. a Gram-negative bacillus outside the Enterobacterales that grows on routine media without fermenting glucose, as its description or a clinical-microbiology source that counts it among the non-fermenting Gram-negative bacilli shows, is a non-fermenting Gram-negative bacillus; one that ferments glucose, and a fastidious one, growing only on enriched media or with added carbon dioxide or less oxygen, as its description or a clinical-microbiology source shows, whether it ferments glucose or not, is a fermenting or fastidious Gram-negative bacillus; and one that grows on routine media and whose descriptions give it a mainly respiratory metabolism in which fermentation may also occur is a variably fermenting Gram-negative bacillus, which a genus whose descriptions are silent on its metabolism never is;
5. a fungus that grows as single cells, a budding yeast of the Saccharomycotina or a basidiomycetous yeast, is a yeast, and a filamentous fungus is a mould, the black yeasts and the dimorphic fungi included, which also grow as yeasts.

A species whose genus carries no `Id`, and whose genus's properties the sources leave too open to place it, sits by these conventions applied to its own properties as its description gives them, and to its genus's where that description is silent.

Where these conventions and the evidence order below leave a genus's group, Gram reaction, or oxygen requirement open, or where the evidence calls for another, the principal investigator of the NeoIPC Surveillance decides it, and the member's or the assignment's `Reason` says why.

The `Attributes` give every `Id`-bearing bacterial node its **Gram reaction** and its **oxygen requirement**, each from the vocabulary of its `Values`: for the Gram reaction, positive, negative, variable, and not classified by the Gram stain; for the oxygen requirement, aerobic, facultatively anaerobic, microaerophilic, aerotolerant anaerobic, obligately anaerobic, and not determined, for a node no single value describes, such as a genus whose description gives more than one value or a group whose members differ, and for a genus whose oxygen requirement none of the sources named below states. They are attributes rather than levels of the tree, since neither is binary and the two do not nest, so that a count by either overlaps the count by group. A node takes the value of its nearest assignment, itself included, and an assignment beneath one with another value says why in its `Reason`.

Every member and assignment cites its `Evidence`: the DOI of ECDC's protocol where the annex names the infectious agent, and otherwise the DOI or PMID of the peer-reviewed work, or the DOI of the strain record in BacDive, that shows the property its placement rests on, under the evidence rule of item 3 of [Reconciling the Ontology With Its Sources](#reconciling-the-ontology-with-its-sources). A Gram reaction or oxygen requirement assigned to a phylum or another higher taxon rests on work that states it for the taxon as a whole, such as its description, a review, or a study of its members. A property of a genus rests on the first of these that states it, a `Reason` naming which wherever it is not item 1:

1. the description of the genus, as first published or as emended, with the tables of the same work that it refers to or that give the genus's own properties, or its chapter in Bergey's Manual of Systematics of Archaea and Bacteria;
2. for a genus formed from species of an older genus, the description of that older genus, cited with the work that formed the genus;
3. a description of its family that states the property for the whole family;
4. the descriptions of its species, their tables included, where that of every species in the genus, as LPSN's correct names count them, states the property, as the description of its only species does for a genus of one.

Where none of these states a genus's oxygen requirement, a peer-reviewed review or clinical-microbiology source that states it for the genus does, as a clinical-microbiology source may show a Gram-negative bacillus non-fermenting or fastidious.

Where none of these settles a genus's oxygen requirement or its growth on routine media, the records of the culture collections that hold the type strains of all its species do, as [BacDive](#bacdive) gives them: the collections' own entries, never BacDive's predictions or automatic annotations. A species placed by its own properties takes them from the records of its own type strain.

## Reconciling the Ontology With Its Sources

The ontology is reconciled with each source's own bulk download, never with pages scraped from its website: LPSN's export of prokaryotic names, MycoBank's list of fungal names, ICTV's Master Species List and Virus Metadata Resource, and the NHSN Organism List's workbook. What a download does not carry, such as the notes on a name's LPSN page, is read from the source's page for that record, one record at a time, and MycoBank's web services, read the same way, give the records that changed after its list was exported.

1. **Names and records.** Each node's name, rank, and record identifier are checked against the download of its source, the one its `ConceptSource` names. A node whose source is NeoIPC is NeoIPC's own, and no download covers it. A bacterial concept takes the name that the List of Recommended Names for bacteria of medical importance applies where it gives one, and LPSN's correct name otherwise; the export's "recommended for medical use" misses some names that list applies, so the note on the name's LPSN page decides. A name that gives way stays as a synonym with its `Id`, and a concept whose taxon LPSN gives no correct name, such as a name that is not validly published, keeps its name, with a `Comments.Background` saying why. A fungal concept takes the name MycoBank gives as current and sits where MycoBank classifies that name's record; where MycoBank's records disagree on the name, as where the one it gives as current is an orthographic variant or invalid while a legitimate name of the same taxon exists, the concept takes the name that agrees with the genus it sits in, with the other name as its synonym; since both keep their `Id`s, the two can change places, losing nothing, once MycoBank's records agree. A MycoBank node's `ConceptId` is the ID of its record in MycoBank's database and its `MycoBankNr` that record's MycoBank number, both permanent; a link to a name takes the MycoBank number. A higher taxon cites the legitimate record of its name where one exists. Where MycoBank's records disagree, as where a genus's record names another genus as current while its type species stays current in it, or where MycoBank files a genus that is no fungus under Fungi, the node's `Comments.Background` says where the list places it and why. A virus concept takes the name, rank, and lineage that ICTV's newest Master Species List gives its taxon, and that release's node as its `ConceptId`, while a synonym, a former name, keeps the node of the release whose name it carries, the newest such release for a synonym new to the list; the `IctvId` links a taxon's nodes across releases. A species that a release splits stays, with its `Id`, as a synonym of a NeoIPC group that holds its successors. A NeoIPC group of viruses covers the species whose isolates ICTV's Virus Metadata Resource gives the names, or abbreviations, of the viruses the group's name denotes, and holds the taxa it covers where they share one parent: whole species, whole genera, or groups or serotypes of its own; a group of the types of one species sits beneath that species, or beneath the group that holds it; and any other group stays a leaf whose `Comments.Background` says which species it covers, or which genera where those hold too many species to name.
2. **Common commensals.** The NHSN Organism List's rows are matched to the ontology's nodes by name. A node's own name, its synonyms, and its concept's names form one cluster, and the most specific match wins: the cluster first, then the lineage at genus level or below, NeoIPC's groups included, then the genus named in the row, then higher ranks. Where the rows that the most specific match reaches disagree, as where an infectious agent's names fall under two genus rows, a row that counts it a common commensal decides, since NHSN counts it one when it is reported under that name. A NeoIPC group matches the row that names the same group in NHSN's words, as *Coagulase-negative staphylococci* matches "Staphylococcus, coagulase negative", and *Viridans streptococci* "Viridans group streptococci". NHSN names viruses by their common names, which are matched to the ICTV species whose isolates ICTV's Virus Metadata Resource gives those names or abbreviations, and to the list's own names with NHSN's forms read as the list's, such as a plural ("Human parainfluenza viruses"), a type number ("Human immunodeficiency virus type I"), a "Human" that the list's name does without ("Human echovirus"), and "encephalomyelitis" for "encephalitis" ("Venezuelan equine encephalomyelitis virus"); a virus row that still matches no node, such as "Arenavirus", leaves no status open, since NHSN lists no virus as a common commensal. Where NHSN names exceptions ("Bacillus, not B. anthracis"), they are combined as a union, and both of the names NHSN gives a row are used, its display name and the SNOMED CT preferred term. A node takes NHSN's status by default; where NHSN is silent, the contamination test below decides. The list departs from NHSN only where the evidence calls for it, as for an infectious agent that NHSN counts as a common commensal but that causes sepsis and meningitis in newborns, or a zoonotic one, and only with the sign-off of the principal investigator of the NeoIPC Surveillance; the node's `Comments.CommonCommensal` then says that its status departs from the NHSN Organism List (2024), and why. A reason whose evidence differs between newborns and adults says so.
3. **Evidence.** `Comments` cite the sources below by their records and rows, the NHSN Organism List by its name and year, as "NHSN Organism List (2024)", and any other evidence only from peer-reviewed work, by its digital object identifier (DOI) or PubMed identifier (PMID) rather than its authors' names. A conference abstract is no such evidence, since abstracts often lack proper peer review. Other work counts where its journal or series, or for a book its publisher, is listed by Finland's Publication Forum (JUFO, <https://jfp.csc.fi/>), Norway's register of publication channels (Kanalregisteret, <https://kanalregister.hkdir.no/>), or both, national registers that publish their criteria, and every register that lists it rates it at level 1 or higher for the year the work appeared; for work that appeared before a register first rated its venue, that first rating counts, and a journal's former title counts by the rating of the journal that continues it.

The `CommonCommensal` flag follows the classification in the NHSN Organism List, except where a node's `Comments.CommonCommensal` records that NeoIPC departs from it, and why. The protocol defines a common commensal as an infectious agent commonly present on epithelium-covered body surfaces, such as the skin, whose growth in a blood culture makes contamination more likely than a recognized pathogen's growth does: the flag is **not about (human) commensalism per se but about blood-culture contamination** at sampling, where the patient's own skin flora plays the dominant role. Beside that flora, NHSN lists some environmental bacteria that contaminate blood cultures, such as most *Bacillus* species, and it lists no fungus, so every fungus stays a recognized pathogen. Wherever NHSN is silent, with no row reaching the infectious agent by the matching that item 2 of [Reconciling the Ontology With Its Sources](#reconciling-the-ontology-with-its-sources) describes, the contamination test decides, the protocol's definition put as a question, which also guides judgement when researching a specific infectious agent: *"is this infectious agent commonly present on the skin or mucous membranes, so that a positive blood culture more plausibly reflects contamination at sampling than true bacteraemia?"* Human skin and mucosal flora (such as coagulase-negative staphylococci and viridans streptococci) answer **yes** → common commensal; zoonotic and frankly pathogenic infectious agents answer **no** → not a common commensal.
